# Design: Dashboard Real-Data Pass

Generated by /office-hours on 2026-09-01
Branch: main
Status: APPROVED (Approach B)
Mode: Builder (internal tool enhancement)

## Problem Statement

The Executive Dashboard mixes live data with hardcoded sample series and
permanently-dead cards, and its one headline number is wrong. Verified against
the live API on 2026-09-01:

- The **Applications KPI shows 5,000; the truth is 15,449.** The unbounded
  `GET /Applications` caps at 5,000 rows; `GET /Applications/paged?pageSize=1`
  returns the exact `totalCount` for a one-row payload.
- Every visit downloads the full Applications table **twice** (KPI count in
  `loadCounts`, again in `appStore.fetchApplications` for a 5-row table) —
  the unbounded load this backend is known to collapse under.
- `/BillingDetails` 500s permanently → the **"Service Degraded" badge is on
  every load** (cry-wolf) and the Billing doughnut is always dead.
- Six KPI cards are permanently zero (Invoices, Active Sessions, VLANs, LCPs,
  LCNAPs, LCNAP Ports — all 0 rows in the DB) and the Invoice doughnut is
  always empty. Real infrastructure truth lives in `LcpNapLocations` (the map
  card already derives 1,571 nodes / 23,144 ports from it).
- Five charts are fake (Bandwidth, Plan Distribution, Revenue/ARPU, Node
  Radar, SLA Gauge) behind an apology banner, and the Today/7d/30d/YTD
  buttons only swap fake bandwidth series.
- KPI cards ignore menu permissions — a fallback-menu user still sees every
  operational count.

## Premises (agreed)

1. Every chart shows real API data — fake charts are replaced by real ones or
   removed, and the apology banner goes away.
2. Keep the current layout and design language — same cards, same styling, no
   redesign.
3. Prefer cheap requests (paged `totalCount`, date-filtered) over full-table
   downloads.

## Approach

Considered:
- **A: Minimal cleanup** — remove/fix only; rejected: charts row goes thin and
  the timeframe buttons stay dead.
- **B: Real-data pass** — **chosen**: cleanup plus rebuilding what can be real
  from data that already exists.
- **C: B + deep links & auto-refresh** — deferred: past "enhance what we
  have"; listed under Future Work.

## Plan (Approach B)

### Remove

1. **Bandwidth Traffic chart** — no API series exists; its layout slot is
   taken by the new Applications-over-time trend.
2. **Regional Node Radar + SLA/Uptime Gauge row** — no telemetry API.
3. **Invoice + Billing Status doughnuts** — `/Invoices` is 0 rows and
   `/BillingDetails` 500s; the Applications + Job Orders doughnuts move up to
   share one row.
4. **Six dead KPI cards** — Invoices, Active Sessions, VLANs, LCPs, LCNAPs,
   LCNAP Ports.
5. **The sample-data apology banner** — nothing sampled remains.
6. **BillingDetails, Invoices, RadiusSession, Vlans, Lcps, Lcpnaps,
   Lcpnapports from the dashboard's monitored fetches** — no card consumes
   them any more; the health badge then reflects only endpoints the dashboard
   actually renders, so it stops being permanently "Degraded". (They remain in
   `MONITORED_ENDPOINTS` for the navbar bell; the dashboard filters to its own
   consumers.)

### Fix

7. **Applications KPI = paged `totalCount` (15,449)** — one-row request
   replaces the 5,000-row download in `loadCounts`.
8. **Recent Applications table fetches a window, not the world** —
   `appStore.fetchApplications` moves to `/Applications/filter` with a recent
   date window (falling back wider when empty, as ApplicationList does),
   sorted desc; the dashboard needs 5 rows, not 15,449.

### Add (all from data that already exists)

9. **Applications Trend chart (replaces Bandwidth slot)** — real counts per
   day/week from `dateTime`, fetched via `/Applications/filter` with the
   window set by the existing Today/7d/30d/YTD buttons. The timeframe
   selector finally does something real.
10. **Subscriber Plan Distribution becomes real** — tallied from the trend
    window's `desiredPlan` values (same fetch, no extra request).
11. **Infrastructure KPI cards from `LcpNapLocations`** — LCP NAP Nodes and
    Plant Ports replace two of the removed dead cards, sourced from the same
    data the map card already loads (shared fetch, not a second one).
12. **Permission-scoped KPI cards** — each card carries its menu code
    (`application.all`, `job-orders.all`, …) and hides via `canAccess`, same
    gate as sidebar/routes/omnibox. A fallback-menu user sees no operational
    counts.

### Resulting layout (same design language)

- KPI row: Applications · Job Orders · RADIUS Users · Active Plans · Routers ·
  NAPs · Ports · Users · LCP NAP Nodes · Plant Ports (10 cards, all real,
  permission-filtered)
- Map card (unchanged)
- Row: Applications Trend (wide) + Subscriber Plan Distribution
- Row: Application Status + Job Order Status doughnuts
- Recent Applications table (unchanged look, cheap fetch)
- PDF export keeps working — it already reads `kpiStats`/tallies, which stay
  real.

## Risks

- `/Applications/filter` costs one request per timeframe change (~200 KB for a
  month). Mitigated: tiny compared to today's two 5,000-row downloads.
- Removing cards changes what long-time users see. Mitigated: everything
  removed was permanently 0, dead, or fake.
- If the backend later ships Invoices/Billing data, their doughnuts come back
  by reverting section "Remove #3" — the tally plumbing (`STATUS_SOURCES`)
  stays in place.

## Future Work (deferred, from Approach C)

open it most (dispatch + billing) which single number they check first each
morning — that number should become the first KPI card, and it will tell us
whether a revenue endpoint is worth requesting from the backend team.
